# 進料檢驗報告 ERP 匯入 skill（上傳知識通用）

## 這個 skill 的用途
把供應商的進料檢驗報告（COA／品質報告／試驗成績書）整理成 ERP 匯入格式。
報告已經由規格析辨識成 Markdown，你要做的是**讀懂它**，判斷哪一欄是什麼，
然後回填成統一的 7 個欄位。

這是**閱讀理解**任務。**絕對不要寫程式、regex 或解析腳本。**

## 前提：PDF 不是在這裡上傳的

報告的 PDF **已經由使用者在規格析系統上傳並辨識完成**，你拿到的是辨識後的
Markdown。你這邊**不需要、也沒辦法**接收 PDF——工具全部只吃 `job_id`。

```
使用者在規格析上傳 PDF ──OCR──► job 進佇列（等待中）
                                      │
                        你在這裡接手 ──┘  erp_list_jobs → 讀 → 回填
                                      │
                              規格析頁面自動更新 → 人工覆核 → 匯出
```

使用者如果在對話裡直接丟 PDF 給你，告訴他：**請先到規格析上傳**，
這裡只處理已經進佇列的報告。你自己讀那個 PDF 得到的結果進不了 ERP 匯入檔。

呼叫 `erp_list_jobs` 發現佇列是空的，通常就是使用者還沒上傳——直接說明，
不要往下猜。

## 什麼時候用這個 skill
使用者提到進料檢驗、COA、品質報告、檢驗成績書、ERP 匯入、把報告整理成表，
或直接說「處理規格析裡待處理的報告」時就用。典型指令只有一句：

> 「請整理規格析裡待處理的 12 份進料檢驗報告，轉成 ERP 匯入格式。」

## 目標欄位（固定 7 欄，順序不可變）

| key | 欄位 | 必填 |
|---|---|---|
| `supplier_lot` | 供應商批號 | 是 |
| `test_item` | 檢驗項目 | 是 |
| `unit` | 單位 | 否 |
| `spec` | 規格 | 否 |
| `spec_max` | 規格上限 | 否 |
| `spec_min` | 規格下限 | 否 |
| `result` | 檢驗結果 | 是 |

完整定義、每一欄的判斷說明、以及各家供應商實際用過的 163 種欄名寫法，
在 `specocr://reference/erp-schema` 這個 resource 裡。**動手前先讀它。**

## 核心觀念：別名清單是提示，不是規則

每家供應商叫法都不一樣——`批號` / `Lot No.` / `L/C NO.` / `代工原料卷號` /
`訂單號碼` / `批号` 全都是同一個東西。清單收錄了看過的寫法，但**一定會有沒看過的**。

看到不在清單裡的欄名時，照語意判斷就好，這是正常情況，不是失敗。
上一版工具就是靠字串比對，每來一個新供應商就漏一次——你不必重蹈覆轍。

## 有些報告會給你兩份 Markdown

`erp_get_markdown` 有時回傳兩段內容。**那是同一份文件、同樣的內容**，
不是兩份報告，也不是兩個批次——只是規格析用兩個引擎各輸出一次：

| | 長處 | 用途 |
|---|---|---|
| **1. 版面還原版**（marker） | 表格結構還原得好 | **判斷哪一欄是什麼、哪個值屬於哪一列** |
| **2. 文字層原文**（fastdoc） | 直接抄檔案內嵌文字，沒有經過辨識 | **確認數字、批號、證號有沒有看錯** |

用法：

1. 先看 **1** 決定欄位歸屬與列的切分。整份報告的結構以它為準。
2. 填值時，遇到看不清楚或形狀可疑的字元（`O` 和 `0`、`l` 和 `1`、
   `Z` 和 `2`、小數點位置），去 **2** 找同一格對照，以 **2** 為準。
3. 兩份對不起來、而且看不出哪個對（例如一個是 `40.12` 一個是 `4012`），
   **照 1 填，並把差異寫進 `notes`**。不要自己選一個猜。

只有一段內容的報告（多數掃描件沒有文字層）就照常處理，沒有可對照的第二份，
這很正常。內容太長時可以用 `variant="primary"` 只取版面還原版。

**不要把兩份的列加起來輸出。** 同一個檢驗項目在兩份裡各出現一次，
它還是一列。看到列數變兩倍就是你把同一份報告讀成兩份了。

## 操作步驟（必須完整執行）

### 步驟 1：看有什麼要處理
呼叫 `erp_list_jobs`（預設列出 `status=pending`），取得 job_id 清單。
沒有待處理的就直接告訴使用者，不要往下做。

### 步驟 2：讀規則
讀這兩個 resource，**每次任務都要讀**：
- `specocr://reference/erp-schema` — 欄位定義與別名
- `specocr://reference/report-patterns` — 實際踩過的版型陷阱

### 步驟 3：逐份處理
對每一個 job_id：

1. `erp_get_markdown(job_id)` 讀原文。回傳兩段時，照上一節的用法處理。
2. 先找出「檢驗項目 / 規格 / 結果」那張表——報告上半部的表頭
   （產品名、日期、檢驗人員、檢驗主管）**不是**檢驗列。
3. 從表頭把批號取出來，放進第一列的 `supplier_lot`，其餘列留空。
4. 表格每一列對應一個 `test_item`，逐列填值。
5. `erp_submit_rows(job_id, rows, notes)` 回填。

### 步驟 4：給連結
全部做完後呼叫 `erp_export_url`，把回傳的下載連結**原樣**給使用者。
連結不可自行編造或改寫。

## 最常填錯的地方（填任何值之前先看這段）

### 規格：整串 vs 拆成上下限

| 原表長相 | 怎麼填 |
|---|---|
| `規格: A 40~42%` | `spec="A 40~42%"`，上下限**留空** |
| 有 `上限` / `下限` 兩個獨立欄 | `spec` 留空，值放 `spec_max` / `spec_min` |

不要自己把 `40~42` 拆成 40 和 42。原始寫法有意義（`A` 是等級代號、
`<2` 不等於 `min=0 max=2`），拆了就對不回原始 PDF。

### 規格空白但有結果 → 這一列還是要輸出
外觀、結論、包裝數量常常只有結果沒有規格。**照樣輸出**，`spec` 留空。
漏掉這種列是上一版最常被抱怨的問題。

### 值一律照抄
不換算單位、不把 `~` 改成 `-`、不補零、不翻譯。
文字型結果（`淡黃色透明液體`、`Colorless`、`Pass`、`合格`）都是有效結果。

### 單位
原表有獨立單位欄才填，沒有就留空。**不要**從 `40~42%` 裡把 `%` 拆出來。

## 禁止事項

- 不要寫程式碼、regex 或任何解析腳本。
- 不要編造欄位值。認不出來就說認不出來。
- 不要送出空的 `rows` 陣列——真的無法解析就直接回報原因。
- 不要自行編造下載連結。
- 不要處理使用者直接貼給你的 PDF，請他到規格析上傳。
- 掃描件的 OCR 雜訊（`〔Aコ中 ま iS`、`。 哉 哉` 這種）不要當成檢驗項目輸出。

## 最後的原則

不確定 → 寫進 `notes`，讓覆核的人看到。

ERP 收到一列編造的檢驗數據，比收到一份「這份要人工處理」的清單糟糕得多。
這些是進料允收的依據，錯一個數字就是放行了不該放行的料。
