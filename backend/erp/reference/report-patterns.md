# 檢驗報告版型與已知陷阱

這份文件的每一條都來自實際的覆核紀錄（38 份供應商報告、三輪人工比對）。
既有的 regex 版本每一條都踩過至少一次。你是靠讀懂內容做事的，所以這些
對你來說不該是問題——但要**知道它們存在**，才不會犯同樣的錯。

---

## 一、表頭資訊 vs 檢驗列

報告上半部通常是一塊表頭：產品名稱、生產部門、批號、檢驗日期、檢驗人員、
檢驗主管、備註。**這些都不是檢驗列。**

只有「檢驗項目 / 規格 / 結果」那張表裡的每一列才輸出。表頭裡的批號要取出來
放進第一列的 `supplier_lot`，其餘資訊不進 ERP。

實際犯過的錯：把「AR2402000000502」（應收憑單號碼）當成檢驗項目輸出。

---

## 二、批號在哪裡

批號是最常抓錯的一欄。同一份報告裡可能同時出現：

| 出現的字眼 | 是不是批號 |
|---|---|
| 批號 / Lot No. / BATCH NO / 製造批號 / 生產批號 | 是 |
| L/C NO. / LC Number | 是（有些供應商用信用狀號當批號）|
| 代工原料卷號 (批號) / 捲號 | 是 |
| 訂單號碼 / Order No / D/O NO. | 是（某些供應商唯一的可追溯號）|
| 檢驗單號 (Analysis No) | **不是** |
| 應收憑單號碼 AR. NO. / 證明書編號 | **不是** |
| 客戶編號 / 客戶訂單編號 | **不是** |

一份報告同時有 `LOT NO` 和 `NO` 兩欄時，實際正確的是 `NO` 那一欄——
**看哪一欄的值真的隨批變動**，不要照字面優先順序挑。

多個批號並列時（例如逐捲列出），每一捲各自成列，不要只寫第一筆。

---

## 三、規格：區間 vs 上下限

供應商有兩種寫法，處理方式完全不同：

**寫成一串** → 整串放 `spec`，`spec_max` / `spec_min` **留空**。

```
規格: A 40~42%        → spec="A 40~42%", spec_max="", spec_min=""
規格: 10000 ～ 18000   → spec="10000 ～ 18000"
規格: <2 mm            → spec="<2 mm"
```

不要自作聰明拆成 40 / 42。原始寫法有意義（`A` 是等級代號、`~` 和 `～` 是不同
字元、`<2` 不等於 `min=0 max=2`），拆了就對不回原始 PDF。

**原表本來就有兩欄** → 這時 `spec` 留空，值放進 `spec_max` / `spec_min`。

判斷方式：看表頭有沒有 `上限/Upper Limit`、`下限/Lower Limit`、`Specification
Max/Min`、`Limit upper/lower` 這種成對的欄。

實際犯過的錯：把下限的值填進了規格欄；把實際值填進了規格上限欄。

---

## 四、規格空白但有結果 → 這一列還是要輸出

有些項目（外觀、結論、包裝數量）沒有規格，只有結果。**照樣輸出**，
`spec` 留空即可。漏掉這種列是既有版本最常被抱怨的問題。

同理，文字型結果是有效結果：「淡黃色透明液體」「Colorless」「Pass」「合格」
「OK」都要照抄進 `result`。

---

## 五、單位

- 原表有獨立單位欄才填。沒有就留空。
- **不要**從規格字串裡把單位拆出來（`40~42%` 的 `%` 留在 spec 裡）。
- 掃描件的單位欄特別容易錯：`%` 常被辨識成 `5`、`Item` 被辨識成 `!tom`。
  看到不像單位的東西（數字、句子、鄰欄文字）就留空，不要照抄雜訊。

---

## 六、合併儲存格

Markdown 表格裡，原本的合併儲存格會變成**同一個值重複出現**，或是
**空字串加在旁邊**。常見兩種：

1. 檢驗項目和規格被合併在同一格，中間用換行或空白分隔——
   要按順序拆回一項對一格。例如：

   ```
   | H-01 外觀 H-08 固成份(%) H-16 黏度 | A 淡黃色透明液體 A 40~42% A 10000~17000 CPS | 淡黃色透明液體 40.12 14550 |
   ```

   這是 **3 列**，不是 1 列。三欄的項目數要對得起來；對不起來就是拆錯了，
   重數一次。

2. 表格最下方的結論列被合併成一整條橫格——那是備註不是檢驗列。

---

## 七、多頁報告

一個 PDF 有多張表時先判斷：

- **同一份報告的續頁**（表頭相同、項目接續編號）→ 合併成一份，列接著排。
- **不同批號的獨立報告**（各自有完整表頭）→ 視為不同的報告，
  但仍回填到同一個 job；用 `supplier_lot` 區分列。

---

## 八、掃描件

檔名有「(掃)」的多半是掃描件，OCR 會有雜訊。判斷原則：

- 明顯不成字的內容不要輸出。實際出現過的垃圾：
  `〔Aコ中 ま iS as AR 17 PEK a =] 口`、`。 哉 哉`、`TEM`。
- 數字被拆開（`12K091A 16` 應是 `12K091A16`）可以合理復原，
  但**只在有把握時**做，並在 notes 註明。
- 整份都是雜訊 → 不要硬湊。直接回報「這份需要重新掃描」。

---

## 九、簡體字報告

有些供應商（大陸廠）用簡體：`批号`、`规格`、`实际值`、`检测值`、
`指示名称 Pareameter`。當成正常欄名處理即可，**輸出時不要轉換成繁體**，
值照抄。

---

## 十、最後的原則

不確定 → 寫進 `notes`，讓覆核的人看到。
認不出來 → 說認不出來。

ERP 收到一列編造的檢驗數據，比收到一份「這份要人工處理」的清單糟糕得多。
這些是進料允收的依據，錯一個數字就是放行了不該放行的料。
